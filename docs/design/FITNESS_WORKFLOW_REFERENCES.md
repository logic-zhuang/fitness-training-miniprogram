# 训练主流程参考：先把一次训练走通

核查日期：2026-10-05。用于回应用户试用中“排版混乱、一天多个动作难以理解、结束入口不明显、提交总结无明显变化”的反馈，具体试用环境待确认。本轮是设计研究，不代表下列建议已经实现。

## 调研范围与证据边界

重点阅读两个可公开查看代码的项目：Liftosaur 和 wger。前者更适合参考现场力量训练的交互，后者更适合参考计划与真实记录的关系。没有把 GitHub 星数作为体验质量依据，没有下载或运行第三方代码，没有对这两个产品进行真机验收。

“资料确证”仅表示维护方文档明确描述；“本项目建议”是基于用户场景的设计判断。文档能说明可借鉴的流程，不能证明本项目当前的提交问题已经定位或解决。既有研究见 [FITNESS_REFERENCE_RESEARCH.md](./FITNESS_REFERENCE_RESEARCH.md)。

## 1. Liftosaur：让用户知道当前动作、下一步以及是否已结束

项目入口：[GitHub 仓库](https://github.com/astashov/liftosaur)。

### 资料确证

- 训练时展开下一组的大号输入；勾选完成后启动休息，随后展开下一未完成组。顶部动作导航显示每个动作的已完成组数，支持直接切换。顶部右侧有 Finish；存在未完成组时先确认，结束后进入展示时长、组数等内容的结果屏，再返回首页。[训练记录官方说明](https://www.liftosaur.com/features/workout-screen)
- 开始前展示所选训练日及动作清单。临时增加支持多选，按钮带选中数量；替换动作有独立入口，并明确只作用于本次训练。已有实际数据得以保留。[本次训练调整官方说明](https://www.liftosaur.com/features/changing-a-workout)
- 计划编辑提供按天查看模式，一张训练日卡片可包含多个动作；编辑有独立保存操作。[计划编辑官方说明](https://www.liftosaur.com/features/program-editor)
- 首页区分“开始下一次”和“继续进行中”，结束记录成为可打开的卡片。编辑历史保存会替换该条记录，不会再次执行训练进阶。[历史官方说明](https://www.liftosaur.com/features/workout-history)
- 数据先落设备，再同步；同步有运行及失败提示。其跨设备冲突策略包含以后修改覆盖先修改的行为。[同步官方说明](https://www.liftosaur.com/features/sync-and-offline)

### 本项目建议

采用“当天动作概览 + 当前动作记录”的层级。一进训练页就能看到“胸部训练 · 4 个动作 · 已记 3/12 组”，动作清单一直有明确入口；每次主要操作集中在一个动作，其他动作缩成可展开摘要。保留直接选动作的自由，不强迫固定顺序。

“每组完成”与“整次结束”必须是两种不同层级的按钮。组行只负责记一组；页面固定位置始终有“结束训练”，不让用户滚过所有动作后寻找。进入总结后固定主按钮叫“保存本次训练”，保存成功进入明显不同的结果状态，展示“已保存”、本次摘要、同步状态和“查看记录”。

记录是否保存、计划是否达标分别反馈。例如：“训练已保存；目标完成 7/9 组，本次为部分完成”。用户不能因为尚未达标而误以为提交失败，也不能因为上传失败而丢失已在本机保存的训练。

### 不建议照搬

本项目不引入 Liftoscript、自动加重量、复杂多周网格或会员功能。也不直接采用其训练中编辑长期计划并影响当前训练、或跨设备以后修改覆盖先修改的策略；继续遵守本项目的历史快照、显式目标调整和冲突保护规则。临时换动作的数据关联仍需按本项目目标标识设计，文档中的相似交互不等于可以直接复用业务实现。

## 2. wger：先分清计划日、动作和真实训练

项目入口：[GitHub 仓库](https://github.com/wger-project/wger)。

### 资料确证

- 官方手册把训练日定义为一次训练的多个动作集合，也允许休息日；既支持贴合每周的安排，也支持其他循环。其“需要记录才推进”规则允许至少记录一组后推进。[Routine 用户手册](https://wger.readthedocs.io/en/latest/manual/routines.html)
- API 模型将 Routine、Day、动作位置及动作配置，与 WorkoutSession、WorkoutLog 分离。一次实际训练包含实际组；实际组还保留当时目标，避免日后计划变化抹去对照。[Routine API 文档](https://wger.readthedocs.io/en/latest/api/routines.html)

### 本项目建议

固定用户能理解的层级：一份周计划包含星期一到星期日；某天是一套训练安排；该安排里有多个动作；每个动作有若干目标组。开始某天后，生成一条“本次训练”，逐组记录归属于这一次训练，最后统一保存成一条历史。

例如：周一“胸肩”包含卧推、上斜推、侧平举三个动作，各三组。因此周一是一个安排、三个动作、九个目标组，完成保存后是一条训练记录。周三可以再安排多个其他动作。最多七个星期安排，不是最多七个动作。

计划编辑只填目标，训练页填实际，历史页负责回看；三个场景使用不同标题和主按钮。计划页不出现实际组完成勾选，历史页不自动开始计时。

### 不建议照搬

wger 的“一组记录后推进”不符合本项目已确认的严格达标规则。本项目仍需本次训练自己的目标清单全部达标才点亮安排；部分训练可以保存，两条部分记录不能合并成完成。任意周期、超级组和独立字段配置接口暂时不引入，保留现有 FastAPI 原子快照接口即可。

## 3. 建议先通过的完整路径

以下为本项目待确认的交互合同，不是已实现声明：

1. **选择安排**：首页显示今天安排及动作摘要；用户可以另选星期或开始临时训练。
2. **开始前确认**：显示当天全部动作、各目标组数；主按钮“开始训练”。
3. **逐动作记录**：当天动作清单与总体进度可见，当前动作展开；输入实际数据并明确完成该组。已完成动作缩成摘要，用户可随时返回修改。
4. **结束训练**：固定入口进入总结，冻结计时；未记录项逐动作列出，用户可继续训练或保存部分训练。
5. **保存本次训练**：按钮立即反馈处理中；失败明确显示原因与重试，保留全部内容；不允许无变化的静默返回。
6. **查看保存结果**：显示保存位置及计划状态；“查看记录”能打开刚保存的同一条记录；返回首页能看到对应统计变化。断网时显示本机已保存、等待同步，云端状态单独反馈。

## 4. 设计验收优先于继续增加功能

先用一个含三个动作的星期安排验证：用户不用口头指导，能认清当前动作、切换动作、完成一组、结束、保存，并重新打开同一条记录。再验证“只练两个动作就结束”“输入未勾选”“断网保存”“重复点击保存”“返回继续训练”。

所有失败都应落到可理解的页面状态：缺数据时定位到对应组；还有未完成目标时解释部分完成；本地写入失败时留在总结；仅同步失败时明确本机记录已保留。不能用自动化测试通过替代对这一整条可见交互的验收。
